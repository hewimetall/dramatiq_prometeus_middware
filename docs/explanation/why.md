# Почему delayed gauge расходится с памятью

Предмет — учёт `dramatiq_delayed_messages_inprogress` в Dramatiq 2.2.1. Наблюдаемые числа собраны в {doc}`/reference/what`. Здесь — почему код воркера приводит именно к ним.

## Сообщение с ETA не обрабатывается там, где его задержали

Отложенное сообщение появляется двумя путями, и для воркера они одинаковы.

Явная задержка: `send_with_options(delay=...)`. Брокер кладёт сообщение в очередь с именем `<queue>.DQ` и записывает `options["eta"]`.

Retry: `dramatiq.middleware.retries.Retries.after_process_message` при исключении вызывает `broker.enqueue(message, delay=delay)`. Задержка — это backoff или `Retry(delay=...)`. Отправитель при этом мог вызвать обычный `send()` без `delay`. Сообщение всё равно оказывается в `.DQ`.

Consumer delay-очереди не ждёт ETA на брокере. Он забирает сообщение сразу. `ConsumerThread.handle_message` видит `eta` и делает две вещи подряд: `emit_before("delay_message", message)` и `delay_queue.put(...)`. С этого момента сообщение «в памяти» в том смысле, который написан в help-строке метрики.

Когда `eta` меньше либо равен текущему времени, `handle_delayed_messages` делает другое:

1. `q_name(message.queue_name)` отрезает суффикс `.DQ` или `.XQ`.
2. `message.copy(queue_name=canonical)` сохраняет `message_id`.
3. Из копии удаляется `eta`.
4. `broker.enqueue(new_message)` без аргумента `delay`.
5. `post_process_message(message)` подтверждает исходную копию, ту, что ещё несёт имя `.DQ`.

Дальше каноническую копию забирает consumer обычной очереди. Это может быть тот же процесс или другой. Исполнение актора идёт уже оттуда, через `before_process_message`.

Штатный Prometheus на шаге «положили в память» увеличивает gauge, а на шаге «актор начал работу» пытается его уменьшить. Между этими шагами сообщение уже покинуло `delay_queue`, сменило `queue_name` и могло сменить процесс. Метрика описывает память, а хук уменьшения описывает старт актора. Отсюда все расхождения ниже.

## Почему метки разъезжаются даже в одном процессе

`before_delay_message` берёт `message.queue_name` как есть. В этот момент имя ещё `billing.DQ`, потому что брокер так назвал очередь ожидания.

`before_process_message` берёт `queue_name` уже у копии. Копия создана через `q_name()`, поэтому имя `billing`.

Один и тот же `message_id` даёт `inc` на `billing.DQ` и `dec` на `billing`. Серия `.DQ` остаётся положительной. Каноническая серия уходит в минус. Множество id при этом очищается: процесс один, id в нём есть, `remove` срабатывает. Поэтому по пустому множеству нельзя сделать вывод, что gauge сошёлся. Issue 627 описывает как раз эту картину меток.

Pull request 627 предлагал канонические имена и `livesum`, но не влит. Pull request 876 сводил обе метки через `q_name()` в `before_delay_message` и был закрыт без merge. Исправление меток само по себе не переносит момент уменьшения: id по-прежнему снимался бы в `before_process_message`.

Этот пакет вызывает `q_name` и на увеличении, и на уменьшении. Серия с суффиксом `.DQ` не появляется.

## Почему другой процесс не уменьшает gauge и почему id остаётся

`self.delayed_messages` — обычное множество на объекте middleware. Объект живёт в процессе воркера. CLI Dramatiq поднимает отдельный процесс на каждый worker. Память множеств между ними не общая.

Уменьшение в штатном коде стоит внутри условия «id есть в моём множестве». Процесс, который исполняет каноническую копию, этого id не добавлял. Условие ложно, `dec` не вызывается.

Процесс, который добавил id, `before_process_message` для этого id тоже не видит: он подтвердил `.DQ`-копию в `post_process_message` и на этом закончил. Штатный код на ack delayed gauge не смотрит.

Id остаётся в множестве до смерти процесса. Это прямое следствие того же `if`, а не второй механизм. Так описывает симптом issue 672: gauge в проде не снижается, множество медленно растёт. Автор issue смотрел Redis, 4 воркера, по 2 процесса. При нескольких процессах каноническую копию чаще забирает не тот процесс, который держал ETA, поэтому снаружи виден «вечный» плюс, а не пара `+1` / `-1`.

Пара `+1` / `-1` видна, когда задержка и исполнение совпали в одном процессе. Оба наблюдения совместимы: развилка — попал ли id в множество того процесса, который вызвал `before_process_message`.

Этот пакет снимает id в процессе, который его запомнил, в момент ack или nack `.DQ`-копии. Это тот же процесс, который вызывал `before_delay_message`: `handle_delayed_messages` и `post_process_message` выполняются на его consumer-потоке. Процесс актора для delayed gauge больше не нужен. Если ack канонической копии случится раньше и id совпадёт, первое снятие уже обнуляет учёт, второе ничего не делает: к моменту ack сообщение из `delay_queue` уже извлечено.

## Почему остановка и обрыв соединения оставляют старый учёт

`before_process_message` не вызывается, когда сообщение просто покидает память.

`Worker.stop` останавливает потоки, затем `ConsumerThread.close`. `close` делает `requeue_messages` по элементам `delay_queue`. Это возврат неподтверждённых сообщений в брокер. Актор их не запускал. Штатному Prometheus сообщить нечем: хука на requeue нет, ack нет.

При `BrokerConnectionError` цикл consumer выполняет `self.delay_queue = PriorityQueue()`. Старый объект с сообщениями отбрасывается. Подтверждения нет, брокер позже доставит их снова. Новое чтение снова вызовет `before_delay_message` и снова сделает `inc`. Предыдущий `inc` никто не компенсировал.

Рестарт consumer после исключения тоже заканчивается `close()`: цикл `for message in self.consumer` завершился, `self.running` ещё истинен, код логирует рестарт и закрывает consumer. Сообщения из памяти уходят в requeue тем же путём.

Поэтому уменьшать gauge в `before_process_message` нельзя, даже если починить метки и научить процессы делиться множеством id. Момент «сообщение больше не в этой памяти» наступает раньше и в других функциях.

Этот пакет слушает два места, которых нет среди хуков middleware: обёртка `ConsumerThread.close` и подмена атрибута `delay_queue`. Оба вызывают `release_queue`. Очередь при этом не опустошается пакетом: `close` сам забирает сообщения и отдаёт их `requeue`. Подмена объекта, как в ветке connection error, списывает то, что осталось в старой куче. `after_worker_shutdown` списывает id, которые эти пути не увидели, и затем вызывает `mark_process_dead`.

## Почему режим `all` переживает `mark_process_dead`, а `livesum` не проверяет, жив ли pid

У gauge в `prometheus_client` есть `multiprocess_mode`. Значение по умолчанию — `all`. Штатный конструктор передаёт `livesum` только в `dramatiq_messages_inprogress`. Delayed gauge создаётся без этого аргумента.

Имя файла gauge: `gauge_<mode>_<pid>.db`. `mark_process_dead` перебирает режимы, чьё имя начинается с `live`, и удаляет только их. Файл `gauge_all_<pid>.db` остаётся. Сборщик для режима `all` отдаёт серию вместе с лейблом `pid`, процесс уже мёртв.

`livesum` в выдаче складывает значения и лейбл `pid` убирает. Сложение идёт по файлам, которые обход каталога ещё нашёл. Проверки «процесс существует» в `MultiProcessCollector.collect` нет. Поэтому `livesum` убирает мёртвый вклад только после удаления файла. Graceful shutdown удаляет файл in-progress gauge, потому что режим `livesum` и хук вызывает `mark_process_dead`. Delayed gauge в штатном коде от этого удаления не выигрывает. Убитый `SIGKILL` процесс не доходит до хука, и `livesum`-файл in-progress тоже остаётся. Эксперимент с значением `7.0` после убийства процесса это показывает: выдача держит `7.0`, пока файл на диске.

Имя `livesum` читается как «сумма живых». В клиенте 0.26.0 «живой» означает «файл этого режима разрешено удалять через `mark_process_dead`», а не «сборщик опросил `/proc`».

Этот пакет создаёт delayed gauge с `livesum`, чтобы `mark_process_dead` удалял и его. Дополнительно `reap_dead_processes` перед scrape смотрит pid в имени файла и для мёртвого pid вызывает `mark_process_dead`. Счётчики не удаляются: их файлы не `gauge_live*`, сумма по ним — накопленная история, её как раз нужно сохранить.

Повторное использование pid этот reap не различает: `os.kill(pid, 0)` для нового владельца того же номера успешен. Старый файл тогда остаётся и совпадает с именем файла нового процесса. Поэтому каталог стирают целиком в момент старта группы, а не полагаются на reap.

## Почему комментарий про очистку каталога не совпадает с кодом

При импорте `dramatiq.middleware.prometheus` модуль один раз читает `dramatiq_prom_db` и вызывает `os.makedirs`. Комментарий над константой говорит, что путь очищается перед каждым запуском. Вызова `unlink` или аналога нет.

Родительский процесс CLI Dramatiq брокер не импортирует. Каталог появляется, когда воркер импортирует middleware. Если чистить каталог в этот момент, воркеры сотрут файлы друг друга. Общий путь по умолчанию — один `$TMPDIR/dramatiq-prometheus` на все инстансы пользователя на машине. Рестарт контейнера без нового tmpfs оставляет те же файлы. Два независимых деплоя с этим путём попадают в один `MultiProcessCollector`.

Поэтому стирание стоит в отдельной команде `dramatiq-prometheus`, которая выполняется до `exec` воркеров и делает это один раз. `DRAMATIQ_PROM_CLEAN=0` оставляет файлы, если каталог сознательно общий и его уже стёр entrypoint, стартующий всю группу.

Стирание обнуляет и счетчики этой группы. Так описан multiprocess-режим клиента Prometheus: каталог готовят до старта процессов. `rate()` внутри одного запуска остаётся корректным. Между запусками счётчик начинается с нуля, потому что файлов прошлого pid больше нет.

## Почему один retry даёт две единицы счётчика

`after_enqueue` в штатном middleware смотрит только наличие `options["retries"]`.

Первый enqueue делает `Retries`: у сообщения появляется `retries`, вызов идёт с `delay`, брокер до хука уже подменяет имя очереди на `.DQ`. Счётчик получает `+1` с меткой `billing.DQ`.

Второй enqueue делает `handle_delayed_messages`: `broker.enqueue(new_message)` без `delay`. Копия сохраняет `retries` и несёт каноническое имя. Хук снова видит ключ и добавляет `+1` уже на `billing`.

Это один повтор и две записи в брокер. Вторая запись — транспорт из памяти воркера обратно в рабочую очередь, не новое решение «повторить».

Условие `delay is not None` отделяет эти записи. Нулевой `delay=0` остаётся учётом retry: `0` — переданная задержка, не отсутствие аргумента.

## Что из этого следует для чтения метрик

`dramatiq_delayed_messages_inprogress` в штатном коде нельзя читать как «сколько отложенных сообщений в брокере» и нельзя читать как «сколько их в памяти». Плюс на `.DQ` может быть чужим процессом, который уже отдал сообщение в работу. Минус на каноническом имени может быть уменьшением, которое попало не в ту серию. После рестарта к этому добавляется файл умершего pid.

В этом пакете ненулевое значение — сообщения, которые живые процессы сейчас держат в `delay_queue`, по каноническому имени очереди. Сообщение, которое ещё только лежит в Redis или RabbitMQ и не прочитано, в gauge не входит. Сообщение, которое уже исполняется актор, сидит в `dramatiq_messages_inprogress`, не в delayed.
